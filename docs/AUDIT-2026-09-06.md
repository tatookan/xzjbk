## A-01 · P1：管理员编辑可覆盖并发购买的已售状态

- 位置：`src/modules/script-catalog/service.ts:283`、`:290`、`:309`。
- 证据：编辑先在事务外读取并检查状态，然后进入事务，最终 UPDATE 只按 ID 定位。`version` 只递增，没有作为更新条件。
- 触发顺序：编辑请求读到 available；购买事务锁定剧本、完成扣费并提交 sold；编辑请求继续将状态更新为 available 或 draft。
- 后果：已售剧本可能重新向其他会员开放详情，或被变成草稿使买家无法正常进入详情。已完成订单唯一索引仍会阻止第二笔完成订单，不能把本问题描述成已证明的重复售卖。
- 建议：在同一事务中锁定并重新校验剧本；增加版本冲突检测，防止两个后台编辑互相覆盖。删除流程也应采用一致的锁定顺序。
- 验收：用隔离测试数据覆盖编辑与购买同时发生、两个管理员同时保存，确保订单存在时状态保持 sold，冲突操作返回明确错误。
- 验证等级：源代码及事务交错分析；本轮未执行并发购买。

## A-02 · P1：生产镜像创建目录的命令缺少父目录处理

- 位置：`Dockerfile:37`。
- 证据：runner 使用 `mkdir .next /data/xinzhi-storage`，没有 `-p`，此前没有创建 `/data`；其镜像阶段也没有从其他阶段复制该父目录。
- 后果：标准基础镜像未预建 `/data` 时，runner 构建在此处失败。本地 `next build` 不执行这条命令，因此本地构建成功不能排除此问题。
- 建议：递归创建目录并设置 node 用户所有权；在干净的 Docker 环境构建 runner，启动后实际执行上传与下载。
- 依据：已核对 [Node 22 官方 slim Dockerfile](https://raw.githubusercontent.com/nodejs/docker-node/main/22/bookworm-slim/Dockerfile)，其没有创建 `/data`。
- 验证等级：Dockerfile 与官方基础镜像定义检查。本机没有 Docker，未执行镜像构建。

## A-03 · P2：备份用户配置与私有文件权限不匹配

- 位置：`compose.production.yaml:85`、`Dockerfile:40`、`src/infrastructure/storage/local-storage-provider.ts:46`。
- 证据：应用以 node 用户运行，官方镜像该用户 UID 为 1000；私有文件权限为 0600。备份服务则使用可配置的 BACKUP_UID/BACKUP_GID，部署手册要求填写宿主部署用户 ID。
- 触发条件：宿主部署用户 UID 不为 1000、也不是具有读取权限的用户。只读挂载不会绕过文件系统权限。
- 后果：备份容器无法读取剧本文件，打包失败。默认 UID 同为 1000 的配置不受这个特定问题影响。
- 建议：明确应用与备份身份约定，兼顾私有卷读取权限和宿主备份目录写权限；校验文件也可能继承原 UID，需要在恢复流程中明确所有权处理。
- 验收：在实际生产 UID/GID 下上传文件、创建备份，并恢复到新卷后以应用用户完成读取。
- 验证等级：权限与配置分析；本地 8 个资源文件权限均为 0600，未运行备份容器。

## A-04 · P2：生产构建删除了后端错误日志

- 位置：`next.config.ts:39`、`src/shared/api/handler.ts:71`。
- 证据：生产启用 `removeConsole: true`；统一 API 异常处理和 readiness 异常处理依赖 `console.error`。本轮生产构建后，在服务端 JavaScript 产物中检索不到这两处日志的标识文本。
- 后果：用户收到 500 和请求编号时，运维缺少对应的业务异常原因；数据库审计流水并不能代替运行错误日志。
- 建议：至少保留 error/warn，或使用服务端结构化日志记录请求编号、错误类型与必要上下文，并对敏感字段脱敏。
- 验收：在隔离环境制造可控故障，确认用户只收到通用提示，服务器日志能够按请求编号找到原因。
- 验证等级：配置审查及本轮构建产物检查。

## A-05 · P2：管理员心源调账缺少重复请求保护

- 位置：`src/app/api/v1/admin/users/[id]/points/route.ts:16`、`src/modules/points/service.ts:107`。
- 证据：每次请求都把 delta 重新加到当前余额并插入流水，没有业务操作唯一编号或去重约束。
- 触发条件：服务器已成功记账，但响应因网络问题丢失，管理员认为失败后再次提交同一次操作。
- 后果：同一次补款或扣减被执行两次。行锁保证串行记账，但不能识别重试；前端禁用按钮也不能处理丢失响应。
- 建议：前端为一次调账生成并保留唯一操作编号；服务端在事务内记录该编号，对重试返回原结果，对相同编号不同内容拒绝执行。
- 验收：同一操作重复提交只增加一条流水，余额只变动一次；不同操作即使金额相同也可正常记账。
- 验证等级：API、服务与数据库约束检查；未对现有用户执行调账。

## A-06 · P2：切换账户时前端状态未按用户身份隔离

- 位置：`src/features/script-library/components/demo-context.tsx:48`、`:65`、`:118`、`:247` 附近的详情缓存；共用布局位于 `src/app/(script-library)/layout.tsx`。
- 证据：余额覆盖值、已购 ID、后台用户和订单长期保存在共用 Provider 中；退出仅调用 signOut，没有清空这些状态。数据加载依赖角色和 pending，没有依赖 session.user.id；详情还会优先返回已加载缓存。
- 触发条件：同一页面生命周期中退出再登录其他账户、其他标签页切换到同角色账户，或切换后的刷新请求失败。
- 后果：界面可能沿用前一个账户的余额、购买标记或详情缓存。服务端下载授权仍会核验当前会话，不能据此断言完整文件下载已被绕过。
- 建议：以用户 ID 作为缓存边界；退出或用户改变时立即清空私有状态，取消旧请求，再加载新账户数据；页面局部详情状态也应随身份变化清空。
- 验收：会员 A/B、管理员/会员、同角色跨标签切换，以及刷新失败场景；确认不出现旧余额、旧订单或超出新身份权限的缓存。
- 验证等级：React 状态及依赖分析；本轮未做浏览器账户切换复现。

## A-07 · P2：部署自检会把不完整迁移判为通过

- 位置：`scripts/validate-deployment.ts:68`、`:82`。
- 证据：迁移只检查 `public.__xinzhi_migrations` 表存在，不比较代码要求的迁移数量和哈希；文件只核对大小，不比对已保存的 SHA-256。自检容器以 root 运行，也不能证明应用用户可以读写资源。
- 后果：恢复出旧数据库、迁移遗漏、文件同长度损坏或应用用户权限错误时，自检可能报成功。例如具备初始 media_assets 表但缺少协议字段的旧版本，可以通过现有迁移表检查。
- 建议：比对迁移清单与哈希，校验文件 SHA-256，并以应用身份做实际读写探针。
- 验收：旧迁移、同长度损坏文件和错误属主三个隔离用例必须自检失败。
- 验证等级：自检实现审查；本轮额外只读检查确认当前本地数据的迁移和资源哈希正常，本问题指检查器覆盖不足。

## 正确的现有设计

- API 路由与身份、剧本、交易、心源、海报业务模块有明确分工，初期继续使用模块化单体合理。
- 邀请码存储为带密钥摘要，注册时锁定一次性注册码；协议同意由服务端校验和留痕。
- 购买包含剧本锁、用户锁和事务；已完成订单有每剧本唯一索引，余额及流水一同提交。
- 公开列表不返回导演阐述或试读正文；普通会员详情只读取开放数量的试读行。
- 原文件由私有 StorageProvider 提供；单文件和 ZIP 都会校验完成订单或管理员身份，成功响应禁止缓存。
- 支付宝未接入与 OSS 未实现符合已确认范围，不作为本轮缺陷。

以上是代码检查结论，不代替经过认证的运行验收。
